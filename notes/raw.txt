What it is

A mini LeetCode. A user picks a problem, writes code, and submits it. The judge runs the code on hidden test cases and replies with a verdict: Accepted, Wrong Answer, Time Limit Exceeded, and so on.


The problem it solves

Running strangers' code on your server is dangerous. Their code could:

loop forever and freeze your server
eat all the memory
delete files or read your secrets
use your network to attack others


Where this is used in real life
Coding sites (LeetCode, Codeforces, HackerRank)
College labs and course assignments that grade code automatically
Hiring tests and coding contests
Online code editors and "try it" playgrounds


What you will build
Sign up and log in (JWT)
A list of problems, each with a statement and hidden test cases
Submit code in a language (JavaScript first, then Python and Java)
The code runs inside a locked-down container, once per test case
A verdict and the run time
A queue, so 50 submissions at once don't crash the server
Submission history


Verdicts
Verdict	Meaning
Accepted	Every test case gave the right output
Wrong Answer	The code ran, but an output was wrong
Time Limit Exceeded	The code ran too long and was killed
Runtime Error	The code crashed
Compilation Error	The code did not compile (Java)
Memory Limit Exceeded	The code used too much memory (stretch goal)



How it will work
Client ──► Express API ──► MongoDB (problems, submissions)
               │
               │ add a job
               ▼
          Redis queue (BullMQ)
               │
               ▼
            Worker ──► docker run (the locked room) ──► verdict ──► MongoDB
The user submits code. The API saves it as Pending and replies immediately with a submission ID.
A job goes into the queue.
A worker takes the job, runs the code on each test case inside a container, and compares the output.
The worker saves the verdict. The user checks GET /submissions/:id.

Why a queue? Running code takes seconds. Without a queue, 50 users at once would start 50 containers and overload the machine. The queue lets only a few run at a time and the rest wait in line, like tickets at a counter. (You used Redis in your first project, so this will feel familiar.)




The design in simple words
MongoDB stores users and problems. (It's the database from your MERN projects.)
Each problem has a statement, a time limit, a memory limit, and a list of test cases. Each test case has an input, the expected output, and a flag isSample.
Hidden test cases must never leave the server. If the API sent them out, anyone could write code that just prints the known answers. So the problem page shows only the sample test cases.
Passwords are hashed with bcrypt, and login gives a JWT, as in your Booking System.



Interview Points
Why store test cases inside the problem document?
Test cases belong to one problem and are usually needed together. Since they are small, storing them inside the problem is simple in MongoDB.
Why hide the test cases?
If users can see the test cases and answers, they can cheat. So the backend sends only the information users are allowed to see.
Why connect to the database before listen?
So the server does not accept requests before the database is ready.
Why is isSample false by default?
If we forget to set the value, the test case remains hidden. This is safer.
Why convert email and password to text?
To prevent someone from sending an object like {"$gt": ""} instead of normal text and trying to manipulate the MongoDB query.

What is spawn?
Your Node.js application needs to start Docker.
spawn allows Node.js to start an external program and communicate with it.



What is randomUUID?
UUID stands for Universally Unique Identifier.
The runner uses a unique name for every container so that one submission doesn't accidentally stop another submission's container.



What is fs?
fs means file system.
Your runner needs to:
1. Make a folder for the submission.
2. Save the submitted source code.
3. Delete the folder when execution finishes.



What is os?
os.tmpdir() gives Node.js the operating system's temporary folder.
The runner uses this location to create temporary submission folders instead of saving every submission permanently in your project.



When someone submits code, the runner follows these steps.
1. Create a temporary folder
   Save the submitted code in a file, such as main.js.
2. Start a restricted Docker container
   Run the code inside an isolated environment, with limits on its resources and permissions.
3. Send the test input
   For example, send 3 4 to the program.
4. Collect the output
   Capture what the program prints, while limiting how much output is kept.
5. Enforce a time limit
   If the program runs too long, stop its container.
6. Clean up and return the result
   Delete the temporary folder and report the output, exit code, execution time, and whether a limit was exceeded.





Interview points
How do you stop an infinite loop? Docker’s limits don’t stop loops. The judge starts a timer and runs docker kill from outside.
How do you stop code from attacking your server? No network, memory and CPU limits, a process limit, a read-only disk, no extra permissions, and a normal user.
Why save the code in a file? It never touches a command line, so it can’t inject commands. Also no shell is used.
Why a unique container name? We can kill exactly the right one, and many runs can happen at the same time.
Why cap the output? A program that prints forever could fill your server’s memory.
How do you tell a timeout from a memory kill? Both exit with 137, so we record a timedOut flag.
Why finally? The temp folder must be deleted on success, timeout, and crash alike.
